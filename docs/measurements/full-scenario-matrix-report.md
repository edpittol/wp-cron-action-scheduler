## The masking finding: a guard inside PHP cannot return a status (issue #35)

### `http-cron-armed`

Guard section 1 -- the block runs INSIDE WordPress, as a mu-plugin, after core's `wp-cron.php` has already called `fastcgi_finish_request()`.

- Status the client read: **200**
- Status nginx logged: **200**
- Status PHP-FPM logged: **200**
- Status PHP held at shutdown, after the response was closed: **200**
- Probe actions drained: **0** of 50

### `nginx-cron-armed`

Guard section 5 -- the same block, moved in FRONT of PHP (nginx). Nothing has been flushed, because PHP never ran.

- Status the client read: **403**
- Status nginx logged: **403**
- Status PHP-FPM logged: **none**
- Status PHP held at shutdown, after the response was closed: **none**
- Probe actions drained: **0** of 50

What the two rows above establish together, and what each on its own cannot:

1. **The guard works either way.** Both rows drained zero. Outcome never came from a status.
2. **Only the outer layer can say so.** Section 1's client reads a success; section 5's client reads the refusal.
3. **The masked 403 is not hidden somewhere server-side -- it does not exist.** This is the claim issue #35 required be verified rather than assumed, and the verification is the two "status" lines under `http-cron-armed`: PHP-FPM logged the flushed status, and PHP's own status at shutdown was still the flushed status. A guard's `http_response_code( 403 )` after `fastcgi_finish_request()` is refused outright -- measured directly, and independently of WordPress, by the isolation proof (`bin/stack measure-fastcgi-isolation`, committed under `results/`): its `flush-then-status` file records `attempted_status` 403, `set_call_returned` false, and a post-flush status read back as 200, while its `status-then-flush` control -- same call, nothing flushed first -- records 403 accepted and observable.

The cost of that visibility is the next section's counter-example: nginx cannot read `DISABLE_WP_CRON`, so section 5 blocks a site that still depends on the web loopback.

## The fleet caveat: what an nginx-layer block cannot do (issue #36)

Both rows below run with `DISABLE_WP_CRON` **false** -- a site that has not opted out of core's own loopback, and therefore still depends on `wp-cron.php` being reachable for cron to run at all.

- `http-cron-armed-cron-enabled` -- Guard section 1 (inside WordPress) checks the constant and deliberately goes inert. Status the client read: **200**. Drained: **50** of 50.
- `nginx-cron-armed-cron-enabled` -- Guard section 5 (nginx) cannot read a PHP constant, so it blocks regardless. Status the client read: **403**. Drained: **0** of 50.

This is the committed counter-example, not a caveat in prose: an **observable status** or a fleet-safe conditional block, at one layer, but not both. A shared guard rolled out across a fleet arms section 5 for every site alike -- including the ones whose cron it silently ends.
